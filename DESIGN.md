# DESIGN.md — Logistics Exception Agent

Technical design for the #6 Logistics Exception Agent. Companion to
[CLAUDE.md](CLAUDE.md) (working rules) and [README.md](README.md) (quickstart).

---

## 1. Problem & thesis

Real logistics exceptions arrive as **noise** — a carrier's autogenerated email, a
half-documented webhook, a driver's photo of a damaged label — and the "right" fix depends
on the situation, not a fixed script. Our thesis:

> An agent is only trustworthy if it (a) works from raw, ambiguous input, (b) executes
> resiliently against unreliable downstream systems, and (c) **proves** its fix against
> authoritative state instead of claiming success.

Everything below serves those three properties.

---

## 2. Architecture

The agent is a **hand-rolled `plan → tool → observe` loop** (no LangChain). One `chat()`
call per turn; the model either calls a tool or emits a final answer. Provider failover
(Gemini→Groq) and the structured trace are generic; the logistics specialization is the
system prompt + the tools + the mock system.

```
                 ┌───────────────────────────── agent.py ─────────────────────────────┐
 raw artifact ──▶│  SYSTEM_PROMPT (policy)   loop: chat() → dispatch(tool) → observe    │
                 │  guards: verify-before-finish, notify-before-finish, permanent-fail  │
                 └───────┬───────────────────────────────┬─────────────────────────────┘
                         │ chat(messages, TOOLS)          │ dispatch(name, args)
                         ▼                                ▼
                     llm.py                            tools.py ─── reads ──▶ logistics.py
              Gemini ▶ Groq failover        schemas + arg handling      DB • indexes • snapshot
              _clean_schema allow-list      LIVE_ACTIONS gate           diff • is_resolved
                                            state change ───────────▶   execute_state_change
                                                                        (idempotency + retry +
                                                                         transient/permanent)
```

### What we changed vs. the generic scaffold
- **`agent.py`**: swapped `SYSTEM_PROMPT` for the logistics policy; `MAX_ITERS` 8→12; added
  active-shipment tracking, three guards, and `state_diff` on the return. The loop shape is
  unchanged.
- **`tools.py`**: new logistics toolset + `LIVE_ACTIONS`; `extract_from_document` gained an
  OCR cache fallback; generic web/rag tools dropped from the active `TOOLS` list.
- **New**: `logistics.py` (engine), `make_assets.py` (photo), UI additions in `app.py`.

## 3. The mock logistics system (`logistics.py`)

In-memory `DB`, reloaded from a `SEED` literal by `reset_db()` at the start of every run —
deterministic, reproducible, and rerun-safe (the whole before→after lifecycle lives inside
one `run_agent` call).

### Tables
`shipments` (+ hidden `_fail_*` injection fields) · `orders` · `customers` · `carriers`
(`api_status`, `regions`) · `inventory` · `audit_log`.

### Indexes (O(1) lookups, rebuilt on reset)
`ship_by_order`, `orders_by_customer`, `carriers_by_region`, `ship_by_tracking`. Reads
(`get_shipment`, `list_carriers`, `issue_credit`) resolve through these instead of scanning.

### Snapshot / diff — the differentiator
`reset_db()` deep-copies every shipment (+ its order & customer) into `DB["_snapshot"]` —
the authoritative **"before"**. `diff(shipment_id)` returns `[{field, before, after}]` of
live state vs. snapshot (hiding internal fields, surfacing an order-level credit row).
`is_resolved()` is true when the exception is cleared **or** the shipment was deliberately
`ESCALATED`. A monotonic `seq` replaces wall-clock time so traces are deterministic.

## 4. Pillar 1 — raw input & extraction under ambiguity

Each scenario starts from a different **modality**, and the agent's first job is to recover
structure from it:

| Scenario | Raw input | How it's parsed |
|----------|-----------|-----------------|
| A | Carrier **email** (junk headers, buried `SHP-1001`) | `parse_exception(source_type=email)` |
| B | **JSON webhook** (inconsistent keys, nulls, extra cruft) | `parse_exception(source_type=webhook_json)` |
| C | **Photo** of a damaged label | `extract_from_document` (Gemini vision) → `parse_exception(source_type=ocr_text)` |

`parse_exception` is **LLM-backed** (a focused extraction prompt returning strict JSON) with
a **regex/keyword safety-net** (`SHP-\d+` + an exception-keyword map) if the model output is
unusable. This is genuine entity extraction where fixed rules would fail on the messy inputs.

---

## 5. Pillar 2 — resilient execution (in code, not prompt)

Every state-changing tool funnels through `logistics.execute_state_change(tool, shipment,
mutate_fn, idem_key)`:

- **Idempotency**: a canonical key (e.g. `reroute:SHP-1001:RapidEx`) is cached; a repeat
  call returns the cached result with `idempotent_replay: true` and **does not mutate again**.
  Protects against model repetition and retry double-writes.
- **Bounded exponential-backoff retry**: `with_retry` (delays 0.2/0.4/0.8s) wraps each
  attempt and records a `retry_log`.
- **Transient vs permanent — decided in code**: the mock raises a typed `TransientFailure`
  (fails the first `_fail_after` attempts, then succeeds) or `PermanentFailure` (always).
  `with_retry` **retries only transient**; **permanent fails fast** (no wasted retries) and
  returns `failure_class="permanent"`.

The agent's act-vs-escalate decision is thus driven by a real failure class, not a guess:
- **B** — `reschedule_delivery` is transient (`_fail_after=1`): fails attempt 1, recovers on
  attempt 2. The retry is visible in the trace (`retried ×1`).
- **C** — `reassign_carrier` is permanent: the agent attempts it, gets `permanent`, and
  **escalates**.

### Deterministic loop guards (safety net, `agent.py`)
1. **Permanent-fail short-circuit** — a re-issued call that already failed permanently is
   refused with a "don't retry, escalate" observation.
2. **Verify-before-finish** — a state change without a following `verify_shipment` is nudged.
3. **Notify-before-finish** — resolving/escalating without `notify_customer` is nudged.

## 6. Pillar 3 — one real external call

`validate_address` calls the live **OpenStreetMap Nominatim** geocoder (no API key, proper
`User-Agent`, ~4s timeout, ≤1 req/s). It's real ground truth we don't control — in Scenario
B the messy `20 W 34 St, New York NY` normalizes to the full USPS-style address, visible in
the diff.

**Documented fallback:** on any timeout/error/offline, it degrades to a small local geocode
table (`source: "mock_fallback"`) so venue wifi can't kill the demo. The `source` field
always says which path served the result.

---

## 7. Verify-and-diff, surfaced to the UI

After any state change the agent **must** call `verify_shipment`, which re-reads authoritative
state and returns `{diff, resolved, current_state}`. The Streamlit UI (`app.py`) renders:
- the verify step as a **before/after table** (red strike-through old → green new);
- a persistent **State Diff** panel with a `RESOLVED` / `ESCALATED` badge;
- a **Resilient-execution audit** timeline (per action: ok/fail, attempts, retries).

The judge sees the exact fields that flipped and the retry that recovered — not an unverified
claim.

## 8. Scenarios (each a different tool path)

| # | Path | Demonstrates |
|---|------|--------------|
| A | parse → get_shipment → list_carriers → **reroute** → verify → notify | email extraction + reroute + diff |
| B | parse → get_shipment → **validate_address (real)** → update_address → **reschedule (transient→retry)** → issue_credit → verify → notify | messy JSON + real geocode + retry recovery + multi-action fix |
| C | **extract_from_document (vision)** → parse → get_shipment → list_carriers → **reassign (permanent fail)** → **escalate** → verify → notify | vision + permanent-failure detection + act-vs-escalate |

No single fixed sequence solves all three ⇒ dynamic tool selection is demonstrated.

---

## 9. Safety / human oversight

Three layers cover high-consequence actions:
- **Real customer sends** — **LIVE ACTIONS** (`LIVE_ACTIONS` env / UI toggle, default **off**)
  gates `notify_customer`. Off ⇒ simulated payload, never calls Twilio/Resend. A human
  enabling the toggle *is* the authorization for real outbound.
- **Financial actions** — `issue_credit` has an approval gate (`APPROVAL_THRESHOLD_USD`,
  default $100). At/above the limit the tool returns `require_approval: true`
  (surfaced in the trace as an **approval required** chip); with `REQUIRE_APPROVAL=1` it
  **blocks** with `status: "awaiting_human_approval"` and mutates nothing until a person
  signs off. (Demo credits are $5, below the limit, so scenarios run unchanged.)
- **Escalation** — `escalate_to_human` is a first-class terminal action (scenario C): the
  agent hands a high-value, unrecoverable case to a person, surfaced as
  **ESCALATED TO HUMAN** and an explicit *human intervention: required* line.

Reads never mutate; state changes are idempotent and audited.

## 10. Known risks & mitigations

| Risk | Mitigation |
|------|-----------|
| Gemini free-tier 429 under heavy use | `chat()` fails over to Groq; `extract_from_document` falls back to cached OCR. |
| LLM narrates a tool call as text (skips it) | Content-free history echo + explicit prompt rule + notify/verify guards. |
| Nominatim latency/outage at venue | Timeout + `mock_fallback`; never on the critical mutation path. |
| Model wanders / exceeds steps | `MAX_ITERS=12`; permanent-fail short-circuit; compact observations. |

## 11. What's intentionally out of scope (8h budget)

- A real React frontend via `getdesign`/Resend components (Streamlit can't host them) — we
  adopt the *aesthetic* (dark theme, Material Symbols, Claude-style loader) via CSS instead.
- A persistent database — the in-memory reset-per-run store is the right call for a
  deterministic demo.
